Además consulta el repositorio por cada abogado.
- Corrección: el dominio no debe importar nada. Hay que quitar la propiedad registros. El caso de uso pide los registros mediante el puerto (repositorio.registros_de(id)) y se los pasa al cálculo de dominio.

Hallazgo 2: el caso de uso ignora el puerto y usa la implementación concreta

- Evidencia: app/aplicacion/reporte_costos.py:4 y :11 hacen self.repositorio = JsonRepositorioCostos(). El puerto RepositorioCostos (aplicacion/puertos.py) está definido pero nadie lo usa. http_reportes.py:10 crea el caso de uso a mano en cada petición.
- Problema: la capa de aplicación depende de infraestructura, cuando debería ser al revés. El puerto existe solo de nombre. No se puede cambiar el adaptador ni probar el caso de uso con un repositorio falso. Tampoco hay raíz de composición.

Hallazgo 3: el adaptador HTTP se salta la capa de aplicación y tiene su propia regla de negocio

Por eso salen Bs 350 y Bs 500 (Reporte 2): las dos pantallas no comparten la regla.

Hallazgo 4: la capa de aplicación conoce el formato de la respuesta HTTP

- Evidencia: app/aplicacion/reporte_costos.py:24-38 devuelve un dict con las claves del JSON público en camelCase (abogadoId, costoHora, promedioFirma).

- Corrección: mostrar promedioFirma tal como llega del backend. Si algún cálculo tiene que vivir en el cliente, va en el dominio o la aplicación del frontend, nunca en el componente.

Hallazgo 3: modelos de dominio definidos dentro de las vistas y atados al formato de la API

- Problema: no hay capa de dominio. Cada vista declara su propia versión del modelo, copiada del JSON del backend, y no hay conversión entre el formato de la API y el modelo. Cualquier cambio en la API rompe las vistas directamente.
- Corrección: poner los tipos en dominio/ (Abogado, ReporteCostos, costoHora: number | null). El adaptador HTTP convierte el DTO de la API en esos modelos.

- Problema: los componentes deberían solo presentar, pero aquí coordinan los casos de uso. Esa lógica no se puede probar ni reutilizar.
